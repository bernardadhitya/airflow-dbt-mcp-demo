# Airflow + dbt + MCP demo: mock retail bank

A small, local-only Airflow 3 + dbt project that mocks a retail bank's data platform, for trying out
[astro-airflow-mcp](https://github.com/astronomer/agents/tree/main/astro-airflow-mcp), an open-source
(Apache 2.0) MCP server that works with any Apache Airflow 2.x/3.x through the REST API.

Everything runs in Docker and binds to `127.0.0.1`. Nothing is exposed to your network.

## Layers and DAGs

```
            09:00 WIB daily                on asset update                 once all 3 silver tables update
bronze_customer     ──► bronze.customer     ──► silver_customer     ──► silver.customer     ─┐
bronze_account      ──► bronze.account      ──► silver_account      ──► silver.account      ─┼─► gold_analytics ──► gold.*
bronze_transaction  ──► bronze.transaction  ──► silver_transaction  ──► silver.transaction  ─┘
```

| Layer | Tables | How it's built |
|---|---|---|
| Bronze | `bronze.customer`, `bronze.account`, `bronze.transaction` | dbt seeds, one DAG per table, daily at 09:00 WIB |
| Silver | `silver.customer`, `silver.account`, `silver.transaction` | Incremental dbt models partitioned by `business_date`, one DAG per table, triggered by its bronze asset |
| Gold | 5 analytics tables, below | One DAG, triggered once all three silver assets have updated |

**Partitioning.** `business_date` is the Jakarta calendar date of the transaction, or of the customer or
account record's last change. dbt-postgres has no `partition_by`, so silver models use `delete+insert`
keyed on `business_date`: each run replaces whole business dates, re-processing the newest one loaded plus
the 3 before it (`silver_lookback_days`). Re-runs are idempotent.

**Gold analytics:**

| Table | Question it answers |
|---|---|
| `customer_monthly_cashflow` | Money in, money out and net amount saved into pockets per customer per month |
| `spending_by_category` | Monthly spend per customer by merchant category, with share of wallet |
| `merchant_performance` | Transactions, unique customers, ticket size and busiest hour per merchant per month |
| `p2p_transfer_network` | Who sends money to whom: allowances, split bills, family support, birthday gifts |
| `high_value_transactions` | Outgoing transactions ≥ Rp 1,000,000 and ≥ 5× the customer's median, a starter fraud/AML queue |

Each dbt node runs as its own Airflow task (via Cosmos) followed by its tests. A final `publish_assets` task
marks the table as updated only after the tests pass, and records its row count and latest watermark on the
asset event.

## Run it

Requires Docker with at least 4 GB of memory (8 GB recommended) and [uv](https://docs.astral.sh/uv/).

```bash
cp .env.example .env
docker compose up -d --build
```

- Airflow UI: http://localhost:8080 (admin / admin)
- Warehouse: `postgresql://airflow:airflow@localhost:5433/warehouse` (schemas `bronze`, `silver`, `gold`)

On a fresh start, the bronze DAGs run today's 09:00 WIB load straight away, and silver and gold follow
automatically. After that they run every day at 09:00 WIB.

Stop with `docker compose down`. Add `-v` to also wipe the databases and run history.

## Use the MCP server

`.mcp.json` registers the server for Claude Code in this folder. Open Claude Code here, approve the `airflow` server, and ask away.

For other clients (Claude Desktop, Cursor), use the same command and environment variables:

```json
{
  "mcpServers": {
    "airflow": {
      "command": "uvx",
      "args": ["astro-airflow-mcp@0.9.1", "--transport", "stdio"],
      "env": {
        "AIRFLOW_API_URL": "http://localhost:8080",
        "AIRFLOW_USERNAME": "mcp_viewer",
        "AIRFLOW_PASSWORD": "mcp_viewer",
        "AF_READ_ONLY": "true",
        "AF_TELEMETRY_DISABLED": "true"
      }
    }
  }
}
```

Two independent guards keep it read-only: `AF_READ_ONLY=true` makes the MCP server refuse write tools, and the
`mcp_viewer` user has Airflow's Viewer role, so the API rejects writes anyway. The Viewer role also can't read
connections, so warehouse credentials stay hidden. `AF_TELEMETRY_DISABLED=true` stops the server from sending
usage telemetry to Astronomer.

The MCP server sees Airflow only (DAGs, runs, tasks, logs, assets), not the data in the warehouse.
